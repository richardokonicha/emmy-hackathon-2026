# Kernel IR → PTX compiler

A from-scratch compiler that turns **Emmy's Kernel IR** straight into **NVIDIA PTX**, with no
CUDA C++ step and no `nvcc`. Emmy is used for exactly one thing — loading the IR through
`Graph.from_dict` — and every instruction of the output is lowered by this repository.

```bash
python compile.py path/to/kernel.ir.json > out.ptx
```

That is the whole submission contract. `compile.py` sits at the repository root, reads one
Kernel IR JSON path from `argv[1]`, and writes PTX to stdout.

---

## Why this exists

Emmy compiles PyTorch to CUDA C++ and hands it to `nvcc` to make PTX. That middle step is
slow — roughly 19× the cost of `ptxas` alone — and Emmy's autotuner wants to compile
thousands of kernel variants. This compiler produces the same PTX directly, in about a
second per kernel.

The 41 variants are *not* the open set with the numbers changed. They are new kernels
generated by tracing fresh PyTorch expressions through Emmy's own compiler, then packaged
with the same launch metadata and checked against NumPy references — odd shapes (777-wide
rows, 9×17 softmax, 8×8 attention, 65,537-element reductions), the full scalar-op family
(tanh, gelu, erf, log, pow, sin, softplus, rsqrt, sigmoid), a negative base for `pow`, a
mixed f32/f64 add, two all-f64 kernels, a pow with an f64 operand, and a hand-built
segment-indexed shared-memory tree. Fuzzing and review found twelve real bugs the open
set never exercised: a `Select` statement that only ever ran its last branch, comparisons
inside a ternary, string-valued names in loop bodies, a wrong-base `pow` (exp-of instead of
two-to-the-power-of), an inverted `f32`↔`f64` coercion table, two conversion mnemonics
that this `ptxas` rejects, a cross-warp race in the `f64` reduction shuffle, `pow`
returning NaN for a negative base with an integer exponent, mixed-precision operands that
were never converted, a value stored at the wrong precision, `setmaxnreg` — an
instruction this runner's assembler does not know — and a segment-indexed `TreeHalve`
that dropped the lane term from its slot index and broadcast from the wrong root.

## How it works

The compiler is one recursive walk over Emmy's typed IR tree. Four layers:

| layer | what it does | where |
|---|---|---|
| **Load** | `Graph.from_dict` for the typed tree; the *raw* JSON for shapes, dtypes and `meta.json` | `Compiler.__init__`, `_find_meta` |
| **Prologue** | parameter loads, `cvta.to.global`, `threadIdx`/`lane`/`warp` decode, the tile guard | `emit_prologue`, `stmt_tile` |
| **Walk** | one method per IR node, dispatching on the node's class | `stmt` |
| **Emit** | the translation itself — one PTX idiom per IR kind | `stmt_*`, `expr`, `op_on_regs` |

### The IR vocabulary it handles

Every node kind in the task's reference table that can appear in an evaluation kernel:

`Tile` · `Load` · `Assign` · `Let` · `Accum` · `Init` · `Write` · `Cond` · `Select` ·
`Loop` · `StridedLoop` · `Smem` · `Sync` · `WarpShuffle` · `TreeHalve` ·
`CpAsyncCopy` / `CpAsyncCommit` / `CpAsyncWait` · `ZeroPrologue` · `SetMaxNReg`

and the expressions `Var` · `Literal` · `BinaryExpr` · `TernaryExpr` · `Builtin` ·
`FuncCallExpr` · `CastExpr` · `FlatIndex`.

### Three things that are easy to get wrong

**The argument order is not the IR's.** `TASK.md` is explicit: parameters come from
`meta.json`'s `arg_order`, because Emmy may reorder arguments between pipeline stages. Get
this wrong and nothing crashes — the kernel just reads the wrong buffers and every number is
garbage. `compile.py` therefore reads the order from `meta.json` and treats the IR node's own
`inputs` list as advisory only.

**The grid is not in the IR.** The `Tile` gives the number of *cells*; `meta.json` gives the
launch geometry. The compiler derives the bounds guard from the Tile's `N` and the thread id
from the launch, which is why a 64-cell kernel launched with 256 threads still needs the
`thread_id < N` guard — the IR does not contain it.

**Loops break SSA.** The IR is single-assignment, but a reduction accumulator is one value
written many times. The compiler lets exactly one place write a running total back in place
(`stmt_accum`, with `base=None` folding into the accumulator's own register) while
everything else keeps SSA discipline.

### Shared memory

Small scratch buffers are declared statically (`.shared .b8 name[size]`). When the total
exceeds the 48 KiB static limit the compiler carves one dynamic pool (`.extern .shared`)
and hands each buffer a runtime-aligned offset — that is the matmul path.

### Registers

Fresh virtual registers are handed out per type (`.f32`, `.b32`, `.b64`, `.pred`, plus
`.b16` for half precision) and declared at the top of the entry. `ptxas` does the real
allocation; the compiler does no liveness analysis.

### Hardening for the hidden set

The hidden set is the same five categories with different shapes and ops, so the compiler
degrades loudly instead of silently:

- **dtypes.** f32 is the corpus, but f64 works end to end. f64 reductions exchange values
  through *registers*: the 64-bit value is split into two 32-bit halves, each half is
  shuffled with `shfl.sync.bfly.b32`, and the pair is reassembled. A shared-memory bounce
  would race, because its slot index only knows the lane, so two warps of the same block
  would overwrite each other's value. f64 constants are built from two 32-bit halves because
  ptxas rejects 64-bit immediates in `mov.f64`. f16 is refused with an explicit message: the
  assembler's PTX has no `.f16` type at all, so a half-precision kernel cannot exist on
  this runner.
- **mixed precision.** Emmy stamps an `Assign` with the *promoted* dtype but leaves the
  operands at their own precision, so an f32 + f64 add arrives with one f32 operand and an
  f64 result. The compiler converts the operands to the result's precision before the
  operation, and converts the result again when the destination buffer is narrower.
- **ops.** Every elementwise op Emmy 0.3.11 can emit is implemented, including float
  `floor_divide` / `remainder` / `mod` (PTX has no float remainder, so it is
  `a - floor(a/b) * b`), integer shifts, `bitcast` and `pad`.
- **instructions.** `dev/probe_ptx_mnemonics.py` assembles every mnemonic the compiler can
  emit against the runner's `ptxas` — 79 of 80 succeed. The exception is `setmaxnreg`,
  which this assembler does not know, so `SetMaxNReg` — a register-budget hint with no
  semantic effect — is dropped rather than emitted. The probe also pins down the
  conversion spellings: widening f32 → f64 is `cvt.f64.f32` (no rounding modifier) and
  narrowing f64 → f32 is `cvt.rn.f32.f64` (one required).
- **contract.** If a kernel arrives without `meta.json`, the compiler falls back to the
  IR's own argument order and warns on stderr instead of exiting non-zero. An ancestor
  directory's `meta.json` is adopted only when it names this kernel or holds exactly one
  kernel, so a sibling problem's metadata is never picked up by accident.

## Running it

```bash
pip install -r requirements.txt          # emmy-ml==0.3.11; numpy/requests are for submit.py

python compile.py problems/r01_array_sum/k_sum_1_reduce.ir.json > out.ptx
python submit.py r01_array_sum --compiler compile.py     # compile + run + check
bash scripts/demo.sh                                    # the 3-step walkthrough used in the video
python dev/run_all.py                                    # all 15 open problems
python dev/run_extra.py                                  # all 41 generated variants
python -m unittest discover -s tests -v                  # unit tests
python dev/probe_ptx_mnemonics.py                        # instruction-set check on the runner
```

Python 3.12 or newer. `submit.py` needs a GPU runner; `compile.py` itself needs neither a
GPU nor CUDA.

## Rule compliance

The task requires the translation to be our own. `compile.py` imports only the standard
library plus Emmy's IR classes, and its single Emmy call is `Graph.from_dict`. There is no
`subprocess`, no `nvcc`, no `emmy compile`, and no use of Emmy's CUDA renderer anywhere in
the compiler. `tools/generate.py` (the organizers' problem generator) does call
`emmy compile`, but it builds the *problems* — it is not on the compiler's path.
